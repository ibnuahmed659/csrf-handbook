QAYBTA VI

QAYBTA VI — DHEXDHEXAAD BYPASSES

  • 10 qaybood
  • 6 tusaale

Waxaa jira dhibaato falsafadeed oo ku jirta amniga cyberka. Dhibaatadu waa composition. Waa isku darka qaybaha.

Aan tusaale keeno. Aan yiraahdo waxaan hayaa laba qaybood:

  • Qaybta 1: Waa ammaan.
  • Qaybta 2: Waa ammaan.

Su'aal: Isku darkooda ma ammaan baa?

Jawaab: Maya. Ma aha had iyo jeer.

Laba qaybood oo ammaan ayaa isku daray si ay u sameeyaan vulnerability. Mid kastaa waa ammaan. Laakiin isku darkooda waa khatar.

Lab-ka : Token Not Tied to Session

Lab-kan wuxuu leeyahay CSRF token. Token-ku wuu jiraa. Laakiin laguma xiriirin session-ka. Token-ka user A wuxuu u shaqeyn karaa user B.

Lab-kan wuxuu ku barayaa farqiqa u dhexeeya identity iyo possession. Wuxuu ku barayaa in token-ku uu yahay "valid" laakiin aanu ahayn "belonging".

Aan si qoto dheer u fikirono. Maxay tahay "token valid"?

Jawaabtu waxay ku xiran tahay perspective:

Perspective 1: Server-ku wuxuu yiraahdaa:

"Token-ku waa valid haddii uu ku jiro liiska token-yada."

Perspective 2: User-ku wuxuu yiraahdaa:

"Token-ku waa valid haddii uu aniga ii gaar yahay."

Perspective 3: Attacker-ku wuxuu yiraahdaa:

"Token-ku waa valid haddii uu shaqeyn karo."

Saddexdan perspective waa kala duwan. Server-ku wuxuu ku fikiraa validity. User-ku wuxuu ku fikiraa ownership. Attacker-ku wuxuu ku fikiraa usability.

Server-ku wuxuu isticmaalaa validity si uu u xaqiijiyo ownership. Laakiin validity ma aha ownership. Waa category error.

Tusaale:

: Server-ku wuxuu isku darayaa "valid" iyo "belongs to". Wuxuu u malaynayaa: "Haddii token-ku valid yahay, waa kan user-ka." Laakiin validity waa global. Ownership waa local. Waa kala duwan yahay.

Aan tijaabino

Tallaabo 1: Login account A

  • Login wiener:peter.
  • Change email, eeg Burp.
  • Qabo token-ka: WIENER_TOKEN.

Tallaabo 2: Login account B (incognito)

  • Login carlos:montoya.
  • Change email, eeg Burp.
  • Qabo token-ka: CARLOS_TOKEN.

Tallaabo 3: Isku beddel token-ka

  • Repeater ku dir request-ka carlos.
  • Beddel csrf=CARLOS_TOKEN → csrf=WIENER_TOKEN.
  • Riix Send.
  • Haddii la aqbalo → waa vulnerable.

Lab-ka 5: Token Tied to Non-Session Cookie

Lab-kan wuxuu leeyahay laba qaybood:

  • session cookie — wuxuu aqoonsadaa user-ka.
  • csrfKey cookie — wuxuu xaqiijiyaa CSRF token-ka.

Lab-kan wuxuu ku barayaa in laba qaybood oo ammaan ay isku dhafan si qaldan. Wuxuu ku barayaa in qayb kastaa ay u dhaqmi karto si ka duwan marka la isku daro.

Maxay tahay "csrfKey"?

Jawaab: csrfKey waa cookie oo lagu xaqiijiyo CSRF token-ka. Waa qayb labaad oo amniga.

Su'aal: Maxay u jirtaa qayb labaad?

Jawaab: Sababtoo ah developer-ku wuxuu rabay stateless CSRF. Wuxuu rabay in aanu session-ka u baahnayn inuu kaydiyo token-ka. Wuxuu rabay in cookie-ga uu xaqiijiyo token-ka.

Developer-ku wuxuu rabay simplicity. Wuxuu rabay statelessness. Wuxuu illoobaa in statelessness ay tahay trade-off. Wuxuu illoobaa in cookie-ga uu yahay attacker-controlled haddii CRLF injection jiro.

Dhibaatada:

  • session cookie waa HttpOnly — attacker-ku ma akhrin karo.
  • csrfKey cookie waa non-HttpOnly — attacker-ku wuu akhriyi karaa (haddii XSS jiro).
  • csrfKey cookie lama xiriirin session cookie.

Laba qaybood oo kala duwan. Mid kastaa waa ammaan gudaha. Laakiin xiriirka u dhexeeya waa jaban yahay. Waa composition problem.

Marka Qoraalku Noqdo Code

CRLF injection Waa marka qoraalku noqdo code. Waa marka data noqdo control.

HTTP waa qoraal. Headers waa qoraal. Marka attacker-ku uu geliyo %0d%0a, wuxuu u sheegaa server-ka: "Halkan waa line cusub." Wuxuu qoraalka u beddelaa control.

Tusaale:

Qoraalku wuxuu noqday code. Data wuxuu noqday control. Input wuxuu noqday output.

CRLF injection waa bridge Waa xiriir. Wuxuu u ogolaataa attacker inuu cookie-ga ku soo dhex geliyo browser-ka victim. Wuxuu u ogolaataa attacker inuu qaybta labaad maamulo.

Sida Loo Tijaabiyo

Tallaabo 1: Login wiener

  • Qabo csrfKey iyo csrf.

Tallaabo 2: Tijaabi csrfKey

  • Beddel session → logout.
  • Beddel csrfKey → CSRF token waa la diiday, laakiin lama saarin.
  • csrfKey wuu jiraa laakiin session-ka lama xiriirin.

Tallaabo 3: Tijaabi isku beddel

  • Login carlos (incognito).
  • Ku beddel csrfKey iyo csrf ee carlos → wiener.
  • Haddii uu aqbalo → waa vulnerable.

Tallaabo 4: Tijaabi CRLF

  • Search samee.
  • Repeater ku dir search=test%0d%0aSet-Cookie:%20csrfKey=WIENER_KEY%3b%20SameSite=None.
  • Haddii response-ku soo celiyo Set-Cookie: csrfKey=WIENER_KEY → waa shaqeynaysaa.

Tallaabo 6: Deliver

  • Soo qaado token cusub.

Lab-ka 6: Token Duplicated in Cookie

Lab-kan wuxuu leeyahay double submit: csrf cookie == csrf body. Attacker wuxuu isticmaalaa CRLF injection si uu csrf=fake ugu soo dhex geliyo browser-ka victim.

Lab-kan wuxuu ku barayaa in statelessness ay tahay khiyaali. Wuxuu ku barayaa in "double submit" uu yahay defense jaban.

6.4.2 Falsafadda Double Submit

Double submit waa "Haddii token-ka body-ga iyo cookie-ga isku mid yihiin, request-ka waa la aqbalayaa."

Double submit wuxuu ku salaysan yahay male-awaal:

  1. Attacker-ku ma dhigi karo cookie-ga browser-ka victim.
  2. Attacker-ku ma garanayo token-ka.
  3. Attacker-ku ma saadaalin karo token-ka.

Male-awaalka 1 waa khaldan haddii CRLF injection jiro. Attacker-ku wuxuu dhigi karaa cookie-ga browser-ka victim. Markaas, wuxuu dhigi karaa csrf=fake cookie-ga, kadibna wuxuu diraa csrf=fake body-ga. Labaduba isku mid → la aqbalayaa.

Double submit wuxuu isku halayaa cookie-ga ammaan. Laakiin cookie-ga ma aha ammaan haddii CRLF injection jiro.

Statelessness waa "Ha kaydin state server-ka. Isticmaal cookie-ga."

Statelessness waa trade-off. Wuxuu keenayaa simplicity. Wuxuu keenayaa scalability. Wuxuu keenayaa performance. Laakiin wuxuu keenayaa khatar haddii aan la ilaalin.

Tusaale:

  • Session-based CSRF: Token-ka waxaa lagu kaydiyaa session-ka. Waa stateful. Waa ammaan.
  • Double submit: Token-ka waxaa lagu kaydiyaa cookie-ga. Waa stateless. Waa khatar haddii CRLF injection jiro.

Statelessness. Waa false sense of security.

6.4.4 Sida Loo Tijaabiyo

Tallaabo 1: Login wiener

  • Eeg request-ka: csrf cookie == csrf body.

Tallaabo 2: Tijaabi double submit

  • Beddel csrf body → waa la diiday.
  • Beddel csrf cookie → waa la diiday.
  • Beddel labadaba si isku mid ah → waa la aqbalay.
  • Double submit.

Tallaabo 3: Tijaabi CRLF

  • Search samee.
  • Repeater ku dir search=test%0d%0aSet-Cookie:%20csrf=fake%3b%20SameSite=None.
  • Haddii response-ku soo celiyo Set-Cookie: csrf=fake → waa shaqeynaysaa.

Tallaabo 4: Samee exploit

Tallaabo 5: Deliver

  • Beddel email-ka.
  • Store, Deliver.

CRLF:

CRLF waa Carriage Return + Line Feed. Waa %0d%0a. Waa calaamad oo u sheegta HTTP: "Halkan waa line cusub."

CRLF waa boundary. Waa xuduud. Waa kala qaybin. Marka attacker-ku uu geliyo CRLF, wuxuu u sheegaa server-ka: "Halkan waa qayb cusub."

Qoraal waa data. Code waa control. CRLF wuxuu u beddelaa qoraalka code.

Tusaale:

Qoraalku wuxuu noqday code. Data wuxuu noqday control. Input wuxuu noqday output.

Headers

Headers waa trust boundaries. Waa xuduudaha. Waa qaybaha.

Headers waa qoraal. Waa data. Waa control. Marka attacker-ku uu geliyo CRLF, wuxuu jebiyaa xuduudaha. Wuxuu maamulaa headers.

Tusaale:

  • Set-Cookie waa header.
  • Location waa header.
  • Content-Type waa header.

Marka attacker-ku uu geliyo CRLF, wuxuu ku dari karaa header cusub. Wuxuu maamuli karaa response-ka.
